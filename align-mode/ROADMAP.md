## 0. 四定

- **定目标**：让 AI 在与人类**实时对齐**的方式下产出交付物——每块真正落盘、当场可审、人类可直接改、AI 重读后继续；方向走错时能**安全返工**。
- **定规划**：见 §2。
- **定规则**：可回滚；不手改 profile；`.mjs` 不放 profile 根目录；升级后先跑 `_test/compat-probe.mjs` 再启用。
- **定边界**：**不做**死规则（体积硬限、强制拦截 write）、**不做** plan mode 绑定、**不做**违规检测、**不做** diff 算法升级、**不做**代码 debug 辅助。**红线**：AI 不得回退或覆盖用户的方向性修改；返工必须先备份再对齐。**截止线**：P1+P2+返工 已完成 = 可用。

## 1. 当前实现（已完成）

**一个 AI 自主调用的工具 `align_deliver`** + 一段使用场景说明：

交付即落盘 → 弹出审阅卡（Markdown 渲染全文）→ **你可直接编辑该文件** → 你选择继续 / 按你改后的版本继续 / 纠正方向 / 先解释 → 工具把对应信号返回给 AI。

**关键点：不设硬性限制**。用不用、一次交付多少，由 AI 判断；场景文字里明确写"判断权在你"。

## 2. 阶段计划

### P0 · 工具与场景 ✅ 已完成（含返工）

工具注册、四种 mode（auto/create/append/replace）、五种返回语义、场景段落、32 项单测、兼容探针、两条真机端到端流程。

### P1 · 场景与触发调优（让 AI 用得更准）

| | |
|---|---|
| **目的** | L1 局限是"依赖 AI 主动使用"。既然不用死规则，那就把**场景描述得足够准**，让 AI 的判断更接近你的意图 |
| **做法** | 观察真实使用：记录哪些场合 AI 用了、哪些该用没用；据此打磨场景段落的措辞（是"改进描述"，不是"加规则"）；场景文本可配置，便于按项目调整 |
| **效果** | 该对齐的地方它主动对齐；不该打扰的地方它不打扰 |
| **验收** | 连续 3 个真实任务中，你需要手动提醒"逐块交付"的次数下降 |
| **风险** | 打磨场景容易滑向"写规则" → 每加一句都要问：这是**场景描述**还是**死约束**？ |

### P2 · 用户主改闭环强化 ✅ 已完成

| | |
|---|---|
| **目的** | 让"你直接改 → 它重读 → 润色"成为**可靠**闭环，而不是碰巧成功 |
| **做法** | ① 记录每次交付后的文件 hash；收到「我改过了」时**校验文件确实变了**，未变则提示你确认（避免误点）；② 校验 AI 的后续写入**没有回退**你的改动——若覆盖了你改过的区间，如实报告；③ `echoAfterEditChars` 让你选择是否立刻把当前内容喂回给它（省一轮 read） |
| **效果** | 你的修改有**程序级**保障不被静默吞掉；误点"我改过了"能被发现 |
| **验收** | 模拟"AI 试图覆盖用户改动" → 被检出并报告；你改后未点确认 → AI 不会继续 |
| **风险** | 内容相似度校验可能误判（如只改了空格）→ 用 hash 精确比对，不做模糊判断 |

### P3 · 可选软护栏 ❌ 已否决（你决定不做）

| | |
|---|---|
| **目的** | 提供一个**你可主动开启**的兜底，而不是默认强加 |
| **做法** | 默认关。开启后：单块超过某体积时**提示而不是拒绝**；或对指定路径要求必须经 `align_deliver` |
| **效果** | 你想要的强约束可以开；不想要就完全没有 |
| **验收** | 关闭时行为与 P2 完全一致（零影响） |
| **风险** | 一旦默认开启就退化成死规则 → **默认必须关**，并在文档里写明它违背本插件的设计原则 |

### P4 · 与子代理协作（大片代码）

| | |
|---|---|
| **目的** | 大片代码靠人逐块审效率低。规划清楚后交给子代理按规划执行 |
| **做法** | 你用 `align_deliver` 对齐**规划/约定**（这部分仍需人对齐），然后让子代理按已对齐的约定产出代码 |
| **平台契合** | 子代理内不能调人类交互工具 → 它**本来就不会弹卡**，正符合"代码不逐块审" |
| **效果** | 文档与约定逐块对齐；代码按约定批量执行 |
| **验收** | 子代理产出符合已对齐的约定；偏离时可见 |
| **风险** | 走子代理就没有逐块纠偏 → **约定阶段必须对齐得更严**（刻意的成本置换） |

### P5 · 安装与分发

走 GUI 插件管理器 `install_bundle`；补 locale/图标；写卸载回滚。**desktop profile 被 Electron 独占，此步必须你操作。**

### P6 · 升级回归自动化

| | |
|---|---|
| **目的** | 上游每发新版（rc.5 → rc.6 …），不靠运气 |
| **做法** | 已建 `compat-probe.mjs`：直接读 `app.asar` 实现，逐条断言 8 条契约。固化为"升级后第一步" |
| **效果** | 一条命令判断"这个版本还能不能用"，并指出破裂点 |
| **验收** | rc.3 → rc.5 均已通过（rc.5 已验证） |
| **风险** | 字符串匹配会误报（宁可误报不可漏报）；上游若重构措辞需人工核对 |

## 4. 局限性

### A. 设计边界

| # | 局限 |
|---|---|
| A1 | **依赖 AI 主动使用**（刻意的代价：换来的是自主性与灵活性） |
| A2 | 只覆盖这个工具；AI 若改用 `write` 就绕过对齐（实测它没有） |
| A3 | **不是裁判**：保证"你看到了"，不保证"内容是对的" |
| A4 | 不做代码 debug 辅助（你定的边界） |
| A5 | 无体积护栏（刻意不做） |

### B. 平台约束

| # | 局限 |
|---|---|
| B1 | 卡片形态受限于问答卡：无并排 diff、无行内评论、无多块批量确认 |
| B2 | 子代理内调用不弹卡（live child 不能调人类交互） |
| B3 | 无 UI 环境无法对齐（已写入但明确告知未送达，不假装成功） |
| B4 | 不能新增持久 session 事件 → 交付进度只能内存派生，重启丢失 |
| B5 | desktop profile 由 Electron 独占 → 安装必须走 GUI |
| B6 | 请求 messages 不可改写 → 场景只能经 `systemPrompt` |

### C. 工程风险

| # | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| C1 | **AI 在不对的场合使用** → 打扰 | 中 | P1 打磨场景描述 |
| C2 | AI 在应使用的场合不用 → 失去对齐 | 中 | 同上；必要时你说一句即可 |
| C3 | 「我改过了」误点 | 低 | P2 的 hash 校验 |
| C4 | 中间态不可运行（逐块交付时文件不完整） | 中 | 按文件粒度交付，或先落骨架 |
| C5 | 覆盖冲突（多任务/子代理同写一文件） | 中 | P2 的改动校验 + 交付前 read |
| C6 | **版本脆弱性** | 中 | P6 探针；只依赖 8 条公开契约；不 import 裸包 |

## 5. 已否决的方案（记录理由，避免反复）

| 方案 | 否决理由 |
|---|---|
| **基于 plan mode 补硬约束** | 你明确否决：**插件与 plan mode 无关**；而且 plan mode 不让 AI 动手，正是问题所在 |
| **硬性体积上限（4000 字符/120 行强制拒绝）** | 你明确指出：死规则会干扰 AI 自主判断、不够灵活 |
| **强制拦截 `write`/`edit`** | 同上；改为 AI 自主调用的工具 |
| `llm/stream` 流式拦截 | 拦的是"不算交付的思考文本"；且有死锁与一致性风险 |
| Myers diff | 你说"不要太在意改的是全段还是某一行"；P2 的"你自己改"更好地解决了同一问题 |
| 违规检测（字面/语义不变量） | 你说情形不常见、不要赘余代码、靠人工审查 |
| 手写 KMP / Aho–Corasick | 前提不成立（语义≠精确匹配）；实测引擎比手写 KMP 快 4.7–76 倍 |
